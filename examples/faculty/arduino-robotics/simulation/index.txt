23:T1e23,# GenAI Sandbox – Faculty Exploration Template (Arduino Robotics Code Review Simulation)

## Sandbox Overview
"This sandbox concept is your space to explore AI-enhanced teaching before classroom deployment. Share what you learn, keep materials CC-BY where possible, and flag integrity questions during the monthly pulse. The checklist below keeps governance light; use it as a reminder, not a barrier."

- [x] Transparency: I can explain any AI-generated material included here.  
- [x] Student data & privacy: Submissions anonymized in stored prompts/responses.  
- [x] Licensing: Claude/ChatGPT outputs used only within course; no external redistribution.  
- Notes / Exceptions: Awaiting departmental green light for broader tool procurement.

---

## 1. Exploration Goal Snapshot
- Goal (1–2 sentences): Test an AI-assisted code review workflow that helps students debug Arduino-based lab sketches before instructor feedback so lab time can be used for physics/engineering concepts and safety checks.  
- Intended audience: 24 students in a first-year physics/engineering robotics lab; managed by one physics instructor and a lab technician.  
- Why this matters now: Lab sessions often stall on syntax and wiring errors; the instructor has limited coding background and wants a structured way to triage code issues without losing time for conceptual discussion.  
- Special requirements or constraints (accessibility, departmental needs, etc.): Maintain hardware safety (no unsafe motor commands or wiring changes), avoid full solutions, and document AI vs. human feedback for program review.

## 2. Workflow & Experiment Log
| Step | AI Assist | Human Judgment | Evidence / Notes |
| --- | --- | --- | --- |
| 1 | Student uploads Arduino sketch (`.ino` file) with a short note on what the robot should do; Claude generates feedback on logic, pin usage, and suggested next steps | Student reviews AI comments, flags confusing or hardware-related suggestions | AI response + prompt stored in tracker |
| 2 | Student implements revisions, annotates changes in a brief reflection log (what changed and why) | Instructor or lab tech spot-checks AI suggestions, confirms they do not violate lab safety rules | Revision diff + student notes saved |
| 3 | If AI feedback seems off or touches wiring/motors, student requests in-person review; ChatGPT backup used if Claude unavailable for code structure questions only | Instructor/lab tech corrects misinformation, adds targeted teaching points about physics/engineering constraints | Override log documents human edits and safety decisions |
| 4 | Instructor provides final comments focusing on modeling, measurement strategy, and physics interpretation rather than syntax | Final feedback merged into LMS gradebook or lab log | Instructor summary and time spent recorded |
| 5 | Post-lab survey captures student confidence in working with code and hardware | Instructor compiles results, compares to baseline | Survey summary appended |
| 6 | Instructor updates workflow prompts/templates based on findings | Share takeaways with program coordinator and robotics team | Iteration notes filed in sandbox log |

- Iteration notes: AI occasionally suggested changing delay values and sensor thresholds without considering lab context—prompt updated to remind “suggest fixes with explanation, do not propose new hardware commands or wiring changes.” Students appreciated quick hints but needed guidance distinguishing suggestions from safety-critical decisions.

## 3. Outputs & Artifacts
- Artifact 1 (link / location): Arduino code review packet (AI feedback, student revisions, instructor/lab tech comments) – e.g., `examples/arduino-robotics-codereview-sim-packet.pdf`.  
- Artifact 2 (optional): AI feedback tracker template with override/safety log.  
- Supporting media or walkthrough: Short Loom or lab note showing how AI feedback feeds into the Arduino workflow (compile → upload → test).  
- Audience feedback captured (if any): Most students reported feeling more confident editing code; instructor reported that time spent on low-level debugging dropped noticeably, freeing time for physics discussions.

### Sample Arduino snippet + AI review

```cpp
const int sensorPin = A0;
int sensorValue = 0;

void setup() {
  Serial.begin(9600);
}

void loop() {
  sensorValue = analogRead(sensorPin);
  Serial.println(sensorValue);
  delay(5000);
}
```

Example AI feedback (summarized):
- Notes that the code will work but that a 5-second delay may make debugging slow; suggests using a shorter delay while testing.  
- Reminds the student to document the expected sensor range and what values would indicate a problem.  
- Suggests adding simple checks (e.g., “if reading is always 0 or always max, check wiring or sensor power”) instead of blindly trusting values.  

In practice, students test sketches like this in a controlled environment such as the Dawson [EngLab virtual environment](https://englab.dawsoncollege.qc.ca) before trying them on physical hardware.

## 4. Reflection Check-In
1. **What shifted during the sandbox run?**
   - Lab time was used more for troubleshooting hardware and discussing physics reasoning instead of fixing syntax; students arrived with cleaner sketches to test.
2. **How did AI help or hinder your approach?**
   - Helped by catching missing pin modes, misplaced braces, and inconsistent variable usage; hindered when suggestions ignored sensor ranges or recommended unnecessary changes to delays.
3. **What will you keep, change, or try next?**
   - Keep AI-first review for code clarity; change prompts to emphasize “do not change wiring or introduce new hardware commands”; next, trial a peer-review layer where students comment on each other’s Arduino sketches after AI review.

## 5. Verification Snapshot
| Output / Decision | How I verified it | Confidence (low/med/high) |
| --- | --- | --- |
| AI feedback accuracy on code structure | Spot-checked 10% of responses; corrected a few logic misfires and over-aggressive delay changes | Medium |
| Student reflection logs | Reviewed for evidence of understanding vs. copying, especially around physics meaning of sensor readings | High |
| Privacy and safety compliance | Confirmed anonymized code samples, restricted drive access, and manual verification of any hardware-related changes | High |

- Follow-up questions for coordination (policy, feasibility, other constraints): Need clarity on acceptable use of AI for hardware-related hints; evaluate program appetite for expanding to other lab courses.

## 6. Next Experiment Hooks
- Next idea I want to explore: Introduce AI-generated practice snippets targeting the top three recurring Arduino errors (e.g., misconfigured pins, timing issues, sensor ranges).  
- Support I could use (community feedback, resources, tooling): Input from robotics/engineering colleagues on safe testing patterns; examples from other institutions running similar Arduino labs.  
- Planned artifact (department meeting, sandbox cohort session, etc.): Demo during physics/engineering department meeting and sandbox cohort showcase.

## 1. Exploration Goal Snapshot
- Goal (1–2 sentences): Test an AI-assisted code review workflow that helps students debug Arduino-based lab sketches before instructor feedback so lab time can be used for physics/engineering concepts and safety checks.  
- Intended audience: 24 students in a first-year physics/engineering robotics lab; managed by one physics instructor and a lab technician.  
- Why this matters now: Lab sessions often stall on syntax and wiring errors; the instructor has limited coding background and wants a structured way to triage code issues without losing time for conceptual discussion.  
- Special requirements or constraints (accessibility, departmental needs, etc.): Maintain hardware safety (no unsafe motor commands or wiring changes), avoid full solutions, and document AI vs. human feedback for program review.

## 2. Workflow & Experiment Log
| Step | AI Assist | Human Judgment | Evidence / Notes |
| --- | --- | --- | --- |
| 1 | Student uploads Arduino sketch (`.ino` file) with a short note on what the robot should do; Claude generates feedback on logic, pin usage, and suggested next steps | Student reviews AI comments, flags confusing or hardware-related suggestions | AI response + prompt stored in tracker |
| 2 | Student implements revisions, annotates changes in a brief reflection log (what changed and why) | Instructor or lab tech spot-checks AI suggestions, confirms they do not violate lab safety rules | Revision diff + student notes saved |
| 3 | If AI feedback seems off or touches wiring/motors, student requests in-person review; ChatGPT backup used if Claude unavailable for code structure questions only | Instructor/lab tech corrects misinformation, adds targeted teaching points about physics/engineering constraints | Override log documents human edits and safety decisions |
| 4 | Instructor provides final comments focusing on modeling, measurement strategy, and physics interpretation rather than syntax | Final feedback merged into LMS gradebook or lab log | Instructor summary and time spent recorded |
| 5 | Post-lab survey captures student confidence in working with code and hardware | Instructor compiles results, compares to baseline | Survey summary appended |
| 6 | Instructor updates workflow prompts/templates based on findings | Share takeaways with program coordinator and robotics team | Iteration notes filed in sandbox log |

- Iteration notes: AI occasionally suggested changing delay values and sensor thresholds without considering lab context—prompt updated to remind “suggest fixes with explanation, do not propose new hardware commands or wiring changes.” Students appreciated quick hints but needed guidance distinguishing suggestions from safety-critical decisions.

## 3. Outputs & Artifacts
- Artifact 1 (link / location): Arduino code review packet (AI feedback, student revisions, instructor/lab tech comments) – e.g., `examples/arduino-robotics-codereview-sim-packet.pdf`.  
- Artifact 2 (optional): AI feedback tracker template with override/safety log.  
- Supporting media or walkthrough: Short Loom or lab note showing how AI feedback feeds into the Arduino workflow (compile → upload → test).  
- Audience feedback captured (if any): Most students reported feeling more confident editing code; instructor reported that time spent on low-level debugging dropped noticeably, freeing time for physics discussions.

### Sample Arduino snippet + AI review

```cpp
const int sensorPin = A0;
int sensorValue = 0;

void setup() {
  Serial.begin(9600);
}

void loop() {
  sensorValue = analogRead(sensorPin);
  Serial.println(sensorValue);
  delay(5000);
}
```

Example AI feedback (summarized):
- Notes that the code will work but that a 5-second delay may make debugging slow; suggests using a shorter delay while testing.  
- Reminds the student to document the expected sensor range and what values would indicate a problem.  
- Suggests adding simple checks (e.g., “if reading is always 0 or always max, check wiring or sensor power”) instead of blindly trusting values.  

In practice, students test sketches like this in a controlled environment such as the Dawson [EngLab virtual environment](https://englab.dawsoncollege.qc.ca) before trying them on physical hardware.

## 4. Reflection Check-In
1. **What shifted during the sandbox run?**
   - Lab time was used more for troubleshooting hardware and discussing physics reasoning instead of fixing syntax; students arrived with cleaner sketches to test.
2. **How did AI help or hinder your approach?**
   - Helped by catching missing pin modes, misplaced braces, and inconsistent variable usage; hindered when suggestions ignored sensor ranges or recommended unnecessary changes to delays.
3. **What will you keep, change, or try next?**
   - Keep AI-first review for code clarity; change prompts to emphasize “do not change wiring or introduce new hardware commands”; next, trial a peer-review layer where students comment on each other’s Arduino sketches after AI review.
